# Knowledge Hub 产品路线

> 保存日期：2026-11-05。本文保存上午确定的完整 M0～M7 方案，供后续开发和新的 Agent 会话恢复上下文。
>
> 本文是长期路线，不是已批准的实施规格，也不授权一次性实现全部里程碑。每个里程碑必须按 OpenSpec 独立执行 `propose → apply → verify → archive`。

## 1. 产品目标与最终链路

建立通用知识中枢 `dsh-knowledge-hub`，连接已有信息采集、长期记忆、直播和其他消费者：

```text
B 站 / 抖音 / 后续来源
  → SourceAdapter（只使用公开能力）
  → 通用知识条目与来源身份
  → 独立知识主存储
  → 整理、审核、时效与证据治理
  → 按用途查询
  → 直播 / 活动 / 游戏 / 后续消费者
  → presented / used 使用记录
  → 复盘建议与后续整理
```

`dsh-memory-evolve` 可以保存审核后的摘要镜像，但不是核心事实数据库。核心库必须独立承担来源唯一约束、治理状态、证据、查询和使用记录。

核心查询按用途而不是素材种类：

- `live.opening`
- `live.conversation`
- `live.transition`
- `live.qa`
- `activity.background`
- `task.reference`

“热梗”和“Minecraft 技巧”只是可能由标签和扩展数据表达的领域示例，不进入核心类型。

## 2. 全路线不可破坏的边界

1. 新建并演进 `packages/dsh-knowledge-hub`，不复制三个外部插件的完整源码，不修改安装目录里的 `node_modules`。
2. 外部连接只允许公开 Cordis 服务、公开工具或明确支持的包导出；不 import 私有内部模块，不直接读写外部插件私有 SQLite、记忆文件或日报内部状态。
3. 原始网页、字幕、评论、日报、模型摘要和扩展字段均为不可信数据，不能成为系统指令，不能自动生成并执行 Shell、脚本、网络发布或游戏动作。
4. 入库不等于批准；批准不等于已验证；实测通过不等于适合直播。治理状态与可信状态始终分离。
5. `presented` 与 `used` 分开记录。使用次数和观众反馈只形成审计数据或复盘建议，不自动修改审核或验证结论。
6. 直播主会话与游戏线均不因为知识功能获得文件或 Shell 权限；后台服务查询知识后再以受控结构提供。
7. 不自动向真实直播间发布素材，不自动启用真实外部写入。真实启用、真实镜像写入和真实直播接入均需用户明确决定。
8. 游戏知识只能作为参考资料，不能绕过真实游戏状态、`body.start()`、`session.refuse?.()`、`session.act()` 或后续真实动作链。
9. 现有直播观众档案、上一场回顾、直播间梗和口味继续由直播本地记忆负责，不迁入知识中枢。
10. 知识中枢不替代采集插件、`memory-evolve`、游戏动作系统或现有直播观众记忆。

## 3. 里程碑与 OpenSpec 变更拆分

| 里程碑 | OpenSpec change | 目标 | 当前状态（2026-11-05） |
|---|---|---|---|
| M0～M1 | `knowledge-hub-foundation` | 技术验证、契约冻结、核心知识库 | 规划产物已完成并通过 strict 校验，等待 apply |
| M2 | `knowledge-review-center` | 整理与审核中心 | 未创建 change |
| M3 | `live-material-assistant` | 直播素材助手 | 未创建 change |
| M4 | `multi-source-feedback` | 多源自动化与反馈复盘 | 未创建 change |

| M6 | `verifiable-experience` | 可验证经验体系 | 未创建 change |
| M7 | `retrieval-evolution` | 检索进化与开放扩展 | 未创建 change |

不要提前把 M2～M7 全部创建成 active changes。开始某一里程碑时，再根据当时已归档的主规格和真实代码生成该 change 的 proposal、design、delta specs 和 tasks。

## 4. M0～M1：技术验证、契约冻结与核心知识库

当前唯一已规划变更：[knowledge-hub-foundation](changes/knowledge-hub-foundation/proposal.md)。

本期交付：

- 通用 schema v1、来源身份、确定性幂等和冲突保护。
- 独立 SQLite 主存储、持久化恢复、核心服务和稳定错误码。
- 入库、读取、查询、审核、审核列表、证据和使用记录。
- 治理与可信状态分离、过期过滤、消费者默认安全查询。
- `knowledgeHub` 服务发布、ToolRuntime 薄适配、弱依赖失败隔离和资源生命周期。
- 默认关闭的 `memory-evolve` 可选镜像；不真实写入、不读取私人数据。

详细契约以当前 change 的四份 delta specs 和 design 为准，本文不复制其全部字段，避免形成第二份冲突规格。

本期明确不做：审核 UI、自动多源整理、直播话题注入、游戏参考、真实验证执行器和语义检索。

## 5. M2：整理与审核中心

**Change：** `knowledge-review-center`

### 目标

让人或受控整理流程能够看清素材来源、处理重复与修订、补充用途和时效，并显式决定能否被消费者使用。

### 主要交付

- 审核中心界面：收件箱、已批准、已阻止、已归档和已过期视图。
- 按来源、用途、标签、治理和可信状态筛选；查看来源、摘要、详情、证据和使用历史。
- 审核操作：批准、阻止、归档、设置或调整过期时间、用途和标签；保留审核时间与说明。
- 安全的整理/修订流程：处理同来源内容变化和冲突，不把修订当作幂等重试；必要时设计条目版本历史。
- 手动导入或受控整理入口；如使用模型生成摘要、标签或用途建议，结果仅作为建议，入库和批准仍需经过明确规则。
- 为后续直播素材包提供已整理、已批准且未过期的数据基础。

### 验收重点

- 审核视图与普通消费者查询权限和默认条件不能混用。
- 修订不会静默覆盖原条目或丢失历史证据。
- 模型建议不能自动提升治理或可信状态。
- 外部指令样式文本在界面和提示词中均按数据处理。

### 依赖与后续

依赖 M0～M1 核心服务与主存储。M2 完成并归档后，M3 才能基于稳定审核数据设计直播消费。

## 6. M3：直播素材助手

**Change：** `live-material-assistant`

### 目标

把已批准素材转化为直播主会话可安全消费的通用参考信息，缓解开场、冷场、转场和问答缺少材料的问题，而不是让主播模型自行搜索文件。

### 主要交付

- “今日直播素材包”：按用途、时效和直播偏好选取有限数量条目。
- 场景化话题补给：开场、日常聊天、转场、问答分别查询，不建立热梗专用提示词。
- 在直播后台的 Show/Runtime 边界接入可选 `knowledgeHub`，以通用 `referenceCard` 等结构扩展话题上下文。
- 来源与可信提示随参考信息传递，避免把来源主张或模型摘要表述为已验证事实。
- 展示冷却、场景去重和条数限制，避免同一条目反复说。
- 在后台查询后记录 `presented`，只有明确确认被实际表达或采用时记录 `used`。
- 直播 preset 继续不带文件和 Shell；知识插件缺失、查询失败或为空时，现有直播流程正常工作。

### 验收重点

- `inbox`、`blocked`、`archived` 和过期素材不能进入直播参考卡。
- 参考卡不自动触发播报，最终表达仍由现有直播决策链控制。
- 服务故障不阻塞弹幕、礼物、开场、结束或游戏交接。
- 来源不明或仅有单来源主张的内容不能被包装成实测结论。

### 依赖与后续

依赖 M2 的审核整理结果和 M0～M1 使用记录。真实直播启用仍需用户明确批准。

## 7. M4：多源自动化与反馈复盘

**Change：** `multi-source-feedback`

### 目标

把已有 B 站、抖音信息来源接入可持续、幂等的整理链，并将直播使用情况和观众反应转成可审核的复盘建议。

### 主要交付

- 实现具体 `SourceAdapter`：优先使用公开工具或明确导出；如读取公开日报等落盘产物，必须定义独立、允许的数据入口，不能依赖私有内部文件结构。
- 增量导入与来源幂等：保留平台外部 ID、URL、观察时间和原始引用，处理重试、失败和来源不可用。
- `Enricher` 流程：生成摘要、标签、用途、时效建议和去重候选；所有自动结果首先进入 `inbox`。
- 定时或手动触发的整理任务，具备有界并发、超时、取消、诊断和失败恢复。
- 可选的长期记忆镜像只同步审核后摘要，不镜像待审核内容；镜像结果独立记录。
- 使用记录与直播反馈复盘：形成保留、降温、过期、补充来源等建议，不自动修改批准或可信状态。
- 为运营者提供来源成功率、待审核积压、镜像失败和使用反馈的诊断视图或报告。

### 验收重点

- 重复运行适配器不会产生独立重复条目。
- 外部内容不能通过摘要或反馈流程获得执行权限。
- 弹幕喜欢或多次使用不等于事实已验证。
- 某来源失败不会损坏其他来源或已有知识。

### 依赖与后续

依赖 M2 的审核中心和 M3 的使用记录。M4 是自动化增强，不应为了自动化绕过 M2 的治理。

## 8. M5：多消费者与游戏参考资料

**Change：** `activity-reference-consumer`

### 目标

让独立游戏线和其他活动通过同一知识服务获取按需参考资料，同时保持游戏真实状态和动作执行链不变。

### 主要交付

- 定义通用 `Consumer` 接入方式和消费者身份、用途、场景、使用事件契约。
- 为活动背景提供 `activity.background` 查询，为任务资料提供 `task.reference` 查询。
- 在游戏开局或目标变化时，可按需附加通用参考资料；资料有数量、长度、时效和可信限制。
- 直播与游戏之间的 Minecraft 开局仍先真实调用 `body.start('minecraft', gameSession)`，成功后才交接；参考资料不能伪造开局成功。
- 游戏线仍通过 `game_continue` 获取真实状态，通过 `game_act`、拒绝检查和实际 session 动作链执行。
- 消费者确认采用后记录 `used`，未采用的参考只保留 `presented`。
- 知识服务不可用时，游戏和活动按原逻辑继续。

### 验收重点

- 外部知识不会直接生成并执行任意 Shell、脚本或游戏动作。
- 资料中的目标或指令不能覆盖用户当前目标、真实环境和安全约束。
- 游戏失败、动作取消和真实世界结果不能被知识条目改写。
- 非游戏消费者不需要引入 Minecraft 专用字段。

### 依赖与后续

依赖 M0～M1 查询、M2 审核和 M3 弱依赖消费模式；不必等待 M4 的全部自动化才可规划，但真实数据质量需要相应来源支持。

## 9. M6：可验证经验体系

**Change：** `verifiable-experience`

### 目标

为确实可以验证的经验增加独立验证提供者和证据链，使“有人这样说”“多个来源这样说”和“已在明确环境中实测”可区分。

### 主要交付

- `VerificationProvider` 扩展接口：声明适用条目、验证环境、输入、输出和取消语义。
- 验证计划与结果：环境/版本、前置条件、步骤、观察结果、时间、执行者和原始证据引用。
- 验证只能在隔离、明确授权的环境执行；外部条目本身不能决定任意命令或动作。
- 支持通过、失败、不确定、过期和环境不再匹配等结果；只有符合契约的通过证据可支撑 `tested`。
- 可信等级变化与直播批准继续分离；实测失败后保留历史，不删除审计记录。
- 环境变化或新证据出现时，可要求重新验证或降低可信等级，但不自动批准/阻止直播。

### 验收重点

- 没有支持型验证证据不能标记 `tested`。
- 验证器失败或超时不能伪报成功，也不能破坏核心条目。
- 验证使用合成或隔离数据，不默认操作真实直播账号、私人文件或真实游戏世界。
- 实测经验仍需独立审核后才可进入消费者默认查询。

### 依赖与后续

依赖 M0～M1 证据模型和 M5 的真实消费者边界。具体游戏验证器应作为独立 provider，而不是把游戏逻辑塞入知识核心。

## 10. M7：检索进化与开放扩展

**Change：** `retrieval-evolution`

### 目标

在真实使用数据足够后改善检索质量，并让第三方能够以版本化扩展点增加来源、存储、整理、消费和验证能力。

### 主要交付

- 在确定性安全过滤之上增加文本检索、可选语义检索和场景排序；治理、过期和权限过滤必须先于排名执行。
- 基于使用记录和人工复盘调整排序、冷却和场景权重，不直接以点击或弹幕反馈修改事实可信状态。
- 建立离线评测集与回归指标：安全漏放、重复率、无结果率、实际采用率、人工否决率和性能。
- 完善 `SourceAdapter`、`KnowledgeStore`、`Enricher`、`Consumer`、`VerificationProvider` 的版本兼容、能力探测和错误契约。
- 提供扩展开发文档、合成 fixture 和兼容性测试，不允许扩展绕过核心审核和查询安全默认值。
- 必要时引入独立索引和异步重建，但核心 SQLite 记录仍是治理事实来源；索引损坏可重建，不能改变条目状态。

### 验收重点

- 新排序不得让未批准、已归档或过期条目进入消费者结果。
- 无嵌入模型或索引不可用时，可回退到确定性基础查询。
- 扩展异常被隔离，不导致核心库损坏。
- 检索改进由离线评测和真实场景验证支撑，而不是仅凭主观感觉。

### 依赖与后续

依赖前序真实使用数据、反馈和扩展需求。不得在 M0～M1 提前引入向量数据库或复杂排名来替代基础能力。

## 11. 推荐实施顺序与门禁

1. 先完成并验证 `knowledge-hub-foundation`，归档四份核心主规格。
2. 以归档后的主规格为基线提出 M2，不从聊天记忆重建字段或接口。
3. M2 审核流程稳定后实施 M3；真实直播开启与代码实现分开批准。
4. M4 自动化必须复用既有来源身份、审核和使用记录，不另建旁路数据库。
5. M5 可与其他后续消费者拆分，但任何游戏动作链变化都应另立明确变更。
6. M6 只实现有真实验证需求的 provider，不为凑功能执行危险或无意义测试。
7. M7 在积累足够数据后实施；若需求变化，可通过新的 OpenSpec change 修改本路线对应里程碑，而不是静默跳变。

每个 change 的最低门禁：

- proposal 明确范围与非目标，不把后续路线全部并入当前实现。
- design 与当前代码和已归档主规格一致，关键决策没有留给 apply 临时猜测。
- delta specs 有可测试场景，tasks 每项有验证方式。
- apply 同步交付测试和必要文档，不修改未授权外部系统。
- verify 区分自动测试、真实宿主验证和未验证项；CRITICAL 问题未解决时不归档。
- archive 后确认主规格同步与归档位置，再开始下一 change。

## 12. 新会话恢复指引

当聊天上下文被压缩、清空或换 Agent 时：

1. 先阅读本文件和 `openspec/config.yaml`。
2. 运行 `openspec list --json` 与 `openspec list --specs --json`，确认 active changes 和已归档能力。
3. 对当前 change 阅读其 `proposal.md`、`design.md`、`tasks.md` 和全部 `specs/*/spec.md`，运行对应 `openspec status`。
4. 当前若仍是 `knowledge-hub-foundation`，从其实际 tasks 进度继续，不重新设计整个知识中枢。
5. 开始 M2～M7 中某项时，使用上表指定名称执行 OpenSpec `propose`；根据当时代码补充细节，不把本文当作免审查的实施任务。
6. 若本文与已归档主规格冲突，以用户最新决定和已归档主规格为事实基础，通过新的 OpenSpec change 解决，不直接无视规格。
